**15:34 · Week 04 · D01 @tool 的原理**

<q>
再给我讲解一下@tool的原理
</q>

<a>
`@tool` 的核心作用是把“普通函数”变成可被 LLM/agent 调度的工具对象。它不是只加一个标签，而是把函数封装成统一接口对象，方便框架读取名称、参数说明、校验输入并执行。

1. 包装前是普通函数，调用方式是 `func(value)`。
2. 包装后变量变成工具对象，所以主要调用路径变成 `invoke/ainvoke`。
3. `@tool` 会基于函数名、docstring、签名生成：
   - `name`
   - `description`
   - `get_input_schema()` 对应的输入结构
4. 工具对象在执行时会先校验输入，再调用内部函数逻辑，最后返回标准化结果。

所以你看到 `.name`、`.description`、`.get_input_schema()` 的属性来自工具对象本身，不是原始函数。
原始函数通常仍在内部可通过 `keyword_length.func(...)` 访问，但这是实现细节，不是课程中的首选调用方式。
课程里建议用 `keyword_length.invoke({"keyword": "abc"})` 或 `await keyword_length.ainvoke({"keyword": "abc"})`，而不是 `keyword_length("abc")`。
</a>

**23:40 · Week 04 · system prompt 写在哪里**

<q>
system prompt 在哪里写了？
</q>

<a>
写在 **`weeks/w04-python-tools/agent_demo.py` 第 75 行**，是 `build_demo_agent()` 里 `create_agent()` 的一个参数：

```python
return create_agent(
    model=model,
    tools=[repository_search],
    middleware=[limit],
    system_prompt="先使用 repository_search 查找文件，再根据工具结果回答。不要编造路径。",
)
```

全仓库只有这一处（w01–w03 的历史代码除外）。

## 它是怎么跑到请求里的

调试输出里能看到两个 `"messages"`，位置不同，正好说明了这件事：

**第 4 行**是 LangGraph 链路日志里的，也就是你传给 `ainvoke` 的输入——**只有你那句问题**：

```json
"messages": [{"role": "user", "content": "哪些文件提到了 retry？"}]
```

**第 29 行**是真正发给 DeepSeek 的 HTTP 请求体——**system 被插在了最前面**：

```json
"messages": [
  {"role": "system", "content": "先使用 repository_search 查找文件，再根据工具结果回答。不要编造路径。"},
  {"role": "user",   "content": "哪些文件提到了 retry？"}
]
```

所以 `system_prompt` 不是被存进对话历史的某一条，而是 **`create_agent` 在每次调用模型时临时插到消息列表最前面**。这正是 w03 我们实测发现、并因此改掉一条测试的那个行为：跑完之后去 `result["messages"]` 里翻，是找不到这条 system 消息的。

## 改它会怎样

这句话直接影响模型的行为。比如把"不要编造路径"删掉，模型可能不调工具就自己猜几个文件名；把"先使用 repository_search"删掉，它可能直接用自己的知识回答。

想验证的话，改完用 `--live --debug` 跑，对比两次请求 JSON 里 `messages[0]` 的差别，以及模型是否还发出 `tool_calls`。这个实验花一次调用的钱，但能很直观地看到 system prompt 的作用。

（这个文件属于教师连接代码，改它不影响你的练习和测试。）
